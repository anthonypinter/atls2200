Forms and Buttons

Links and media only go one way. Buttons and forms let visitors talk back: sign up, search, send a message. HTML does a surprising amount of the work, if you choose the right elements.

You'll be able to

  • Choose the right type for a <button>.
  • Build a form from <form>, labelled controls and a submit button.
  • Pick input types, radio buttons, checkboxes, <select> and <textarea> to fit the question.
  • Let the browser validate answers, and know why the server must check them too.

Interacting with users

So far your pages talk and visitors listen. To let them answer, you need two kinds of element: buttons, which do something when pressed, and forms, which collect information and send it somewhere. Both come with keyboard support and screen reader support built in, as long as you use the real elements.

Buttons

A button is made with <button>, and its text goes between the tags:

<button type="button">Show the map</button>

On its own, a button with type="button" does nothing when clicked. JavaScript gives it a job, which you'll do in Week 7. Inside a form, though, buttons already have jobs, chosen by type:

  • type="submit" sends the form. It's the default inside a form, so say it anyway to be clear.
  • type="reset" clears every field back to its starting value. Rarely a good idea: one mis-click wipes everything.
  • type="button" does nothing until JavaScript says so.

Links go somewhere; buttons do something. If clicking it changes the page or the URL, it's a link. If it sends, opens, plays or toggles, it's a button.

The anatomy of a form

A basic form has three parts: the <form> wrapper, one or more label-and-control pairs, and a submit button.

<form action="/subscribe" method="post">
  <label for="email">Email</label>
  <input type="email" id="email" name="email" required>
  <button type="submit">Subscribe</button>
</form>

The <form> element

When the form is sent, each field travels as name=value. The form's action says where to send it, and method says how: get puts it in the URL, post sends it out of sight. A field without a name isn't sent at all.

<input> elements

    
<input> is an empty element that becomes many different controls depending on its type. type="email" gives phones a keyboard with an @ key and checks the address before sending. type="date" brings up a date picker. Use type="text" for everything and you get none of that. Give each input an id (for its label), a name (for the data) and, if it can't be left empty, required.

    <label> elements
    
    
    Every control needs a label. Connect them explicitly, by matching the label's for to the input's id, or implicitly, by putting the input inside the label:
    
    
    <label for="name">Name</label> <input id="name" name="name">
<label><input type="checkbox" name="news"> Email me updates</label>
    
    
    Clicking the label focuses the control, which gives everyone a bigger target, and a screen reader reads it aloud when someone reaches the field. A placeholder is not a label: it disappears as soon as you type.

    Other control types
    
  
    
    
      
      
    • Radio buttons (type="radio") are for picking exactly one option. All the radios in a group share the same name; each has its own value. Add checked to pre-select one, and disabled to make one unavailable.
      • 
      
    • Checkboxes (type="checkbox") are for zero or more options. Each one is independent and has its own name.
      • 
      
    • Drop-down menus are a <select> holding <option>s. They save space when there are many choices.
      • 
      
    • Multi-line text goes in a <textarea>, which has a closing tag. rows and cols set its starting size.
      • 
    
    
    
    A group of radios or checkboxes needs a question. Wrap the group in a <fieldset> and put the question in its <legend>.

    Form validation
    
  
    
    
    Attributes like required, minlength, pattern, min and max, and types like email, make the browser check answers before sending and explain what's wrong. That's client-side validation, and it helps visitors fix mistakes quickly.
    
    
    Note
    Client-side validation doesn't protect a server: anyone can switch it off or send data without your form. Real sites always check again on the server (server-side validation). You need both.

    Key ideas
    
      
      
        
    • Every input needs a label. The label's for must match the input's id exactly.
      • 
        
    • The name attribute is what the data is called when the form is sent.
      • 
        
    • Radio buttons in the same group share one name, so only one can be picked. Wrap the group in a <fieldset> with a <legend>.
      • 
        
    • Use <button type="submit"> to send a form and type="button" for anything else.
      • 
      
    
    
    
    
    
      
    Common mistakes
    
      
      
        
    • Using placeholder instead of a label. It disappears when you type and is often low-contrast.
      • 
        
    • Typing type="text" for everything and missing the free validation and keyboards.
      • 
        
    • Reusing the same id twice, so a label points at the wrong input.
      • 
        
    • Forgetting that browser validation doesn't protect a server. Real apps check on the server too.
