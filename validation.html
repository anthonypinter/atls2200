Validating Your Code

Browsers quietly guess their way around mistakes, so broken code often looks fine until it suddenly doesn't. A validator reads your code like a strict teacher and lists every problem with a line number.

You'll be able to

  • Check HTML and CSS with a validator and read its messages.
  • Fix errors starting from the top of the list.
  • Use DevTools to see how the browser repaired broken HTML.
Read

A second pair of eyes

Browsers are forgiving. If you forget a closing tag or misspell a property, they don't show an error. They guess what you meant and keep going. That sounds helpful, but it means broken code often looks fine in your browser until something unrelated changes, or until someone opens it in a different browser that guesses differently.

A validator doesn't guess. It reads your code against the rules and lists every problem with a line number. There are free ones for HTML and CSS, and you can paste code in or upload a file.

Validators sort their findings into two groups. Errors break the rules and should be fixed. Warnings are suggestions, worth reading but not always wrong.

Always fix from the top down. One early mistake, like an unclosed <div>, can make everything after it look wrong to the validator, producing a long list of errors that disappear once you fix the first one. Fix it, validate again, and repeat.

For CSS, the browser simply skips any declaration it doesn't understand. There's no message; the style just doesn't apply. That silent skip is exactly the bug you're hunting, and the CSS validator will point straight at it.

When HTML is broken, the browser repairs it in ways that can surprise you, such as moving a <div> out of a <p>. DevTools shows the repaired version, so comparing it with your file reveals what the browser changed.

Tip

Validate before handing in any project, and any time something looks wrong and you can't see why. It takes a minute and catches mistakes your eyes skip over.

Play

The tools

Bookmark these. Then try spotting errors yourself below.

HTML

W3C Markup Validator

  1. Choose "Validate by Direct Input."
  2. Paste your whole HTML file.
  3. Click Check.
CSS

W3C CSS Validator

  1. Choose "By direct input."
  2. Paste your stylesheet.
  3. Click Check.
How to read the results
  1. Fix the first error first. One missing bracket can cause ten more errors below it.
  2. Go to the line number it gives, then look at the line just above it too.
  3. Check again after each fix.

What the browser actually built

When HTML is broken, the browser silently repairs it, sometimes in surprising ways. DevTools' Elements panel shows the repaired version, not your file. Pick a snippet: the right side is your own browser's real result.

Key ideas

      
    
        
  • Validate before you hand in work, and whenever something looks wrong and you can't see why.
    • 
        
  • "Errors" must be fixed. "Warnings" are suggestions worth reading.
    • 
        
  • Indenting your code consistently makes missing closing tags and braces much easier to spot.
    • 
        
  • Your code editor's highlighting is a validator too: if colors suddenly look wrong partway down, the mistake is just above.
    • 
      

    

    

      
Common mistakes

      
    
        
  • Fixing errors from the bottom of the list up.
    • 
        
  • Assuming code is fine because it looks right in one browser.
    • 
        
  • Validating a single section instead of the whole file, which creates fake errors about missing tags.
    • 
        
  • Ignoring the CSS validator because "CSS just skips bad lines." That skipping is exactly the bug.
