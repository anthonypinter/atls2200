Accessibility Essentials

An accessible site works for people using a keyboard, a screen reader, zoom, captions, or a phone in bright sun. Most of the work is choosing the right HTML and not breaking it with CSS and JavaScript.

You'll be able to

  • Describe the main kinds of disability and the assistive technologies people use.
  • Use semantic HTML so buttons, links, labels, headings and images work for everyone.
  • Check color contrast, keep focus visible, and hide content without hiding it from screen readers.
  • Test a page with only the keyboard.

So what is accessibility?

Accessibility is the practice of making your sites usable by as many people as possible: people with disabilities, but also people on slow connections, on small screens, in bright sunlight, or holding a baby in one arm.

It isn't an extra feature for a few people. An accessible site has clear structure (which also helps search engines), works on any device, and is easier for everyone to use. In many countries it's also a legal requirement for public and commercial sites.

What kinds of disability are we looking at?

Around 1 in 6 people worldwide has a significant disability. Many use assistive technology (AT) to browse the web.

People with visual impairments

This includes blindness, low vision and color blindness. People may use a screen reader that reads the page aloud (JAWS and NVDA on Windows, VoiceOver on Mac and iPhone, TalkBack on Android), a screen magnifier, or simply the browser's zoom.

People with hearing impairments

Deaf and hard-of-hearing people need text alternatives for audio: captions on video and transcripts for podcasts.

People with mobility impairments

Some people can't use a mouse. They use the keyboard (especially Tab, Enter and Space), switches, voice control or a head pointer. Everything that works with a mouse must work with a keyboard.

People with cognitive impairments

This is the widest group, including learning disabilities, memory problems, ADHD and dyslexia. It's helped by plain language, consistent layouts, clear headings, links that look like links, and helpful error messages.

Implementing accessibility into your project

Accessibility is much cheaper to build in from the start than to bolt on at the end. Use the right HTML as you write it, check contrast when you pick colors, and test as you go: with the keyboard, with zoom, with an automated checker, and, if you can, with disabled users. Many organizations publish an accessibility statement saying what they support and how to report problems.

Accessibility guidelines and the law

The main standard is the Web Content Accessibility Guidelines (WCAG). It's organized under four principles, often remembered as POUR:

  • Perceivable: people can see or hear the content (alt text, captions, contrast).
  • Operable: people can use the controls (keyboard access, enough time, no flashing).
  • Understandable: content and controls are clear (plain language, helpful errors).
  • Robust: it works with many browsers and assistive technologies (valid, semantic HTML).

Laws in many places, such as Section 508 in the US and EN 301 549 in the EU, point to WCAG.

Accessibility APIs

How does a screen reader know what's on a page? The browser builds an accessibility tree from your HTML: every element's role (button, link, heading, text field), its name (the button's text, the image's alt, the input's label) and its state (checked, expanded). The operating system passes that tree to assistive technology.

That's why HTML matters so much. A <button> arrives in the tree as "button, Sign up". A <div> styled to look the same arrives as plain text. WAI-ARIA attributes like role and aria-label can patch the tree when HTML has no suitable element, but the first rule of ARIA is: if a native element does the job, use it.

HTML: A good basis for accessibility

Most accessibility comes from choosing the right element, so semantic HTML brings it with it for free.

Good semantics

  • Well-structured text. Real headings in order (<h1>, <h2>…), paragraphs and lists, not bold <div>s and <br>s. Screen reader users skim by jumping from heading to heading.
  • Clear language. Write "5 to 7" rather than "5–7", and expand abbreviations, or mark them with <abbr>.
  • Logical page sections. <header>, <nav>, <main>, <aside> and <footer> become landmarks people can jump to.
  • Semantic UI controls. A real <button> can be reached with Tab, pressed with Enter or Space, and is announced as a button. A clickable <div> does none of that. Every form control needs a <label>.

Accessible data tables

Use <th> for headers with a scope, and a <caption>, so a screen reader can say which row and column each cell belongs to.

Text alternatives

Every meaningful image needs alt text that says what it shows. Decorative images get an empty alt="", so they're skipped. A <figure> with <figcaption> adds a visible caption.

More on links

  • Links should look like links (underlined, or clearly different) and have visible hover and focus styles.
  • Link text should make sense on its own: "Royal Arch trail guide", not "click here". Screen reader users often list every link on a page.
  • If a link opens a new tab or a file like a PDF, say so in the link text.
  • A skip link at the top ("Skip to main content") lets keyboard users jump past the navigation.
  • Leave space between links and buttons that sit close together, so they're easy to hit.

    CSS and JavaScript accessibility best practices

    Correct semantics and user expectation

    CSS can make anything look like anything, which makes it easy to break what people expect. Keep the conventions: links underlined or otherwise obvious, with distinct :hover, :focus and :visited styles; abbreviations with their dotted underline; buttons that look like buttons; comfortable body text with line-height around 1.5. And never remove the focus outline without putting a clear replacement in its place.

    Color and color contrast

    Text needs enough contrast with its background: at least 4.5 to 1 for normal text and 3 to 1 for large text (WCAG AA). And never use color alone to carry meaning, like a red dot for "closed": add a word or an icon.

    Hiding things

    There are several ways to hide something, and they don't all hide it from screen readers:

    • display: none and visibility: hidden hide it from everyone, screen readers included. Use them for things nobody should get, like a closed menu.
    • A visually hidden class shrinks the element to 1px and clips it. It's invisible on screen but still read aloud. Use it for things only screen reader users need, like a label for an icon-only search button.
    • opacity: 0 makes it invisible but still clickable and read aloud, which is usually confusing.
    .visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
}

    Accept that users can override styles

    People may zoom to 200% or more, set a larger default font, force high-contrast colors, or use their own stylesheet. Build layouts that cope: sizes in rem, no fixed heights on text, nothing that relies on exact pixel positions.

    JavaScript

    JavaScript can make a page more accessible, or much less. Keep it unobtrusive: build the page with real HTML first (a real form with labels and a submit button), then add scripts to improve it, such as checking the form before it's sent. Don't build whole interfaces out of <div>s that only work with a script and a mouse.

    Watch out for mouse-specific events. Anything that happens on mouseover should also happen on focus; anything on mouseout should also happen on blur. In CSS, the same goes for :hover: pair it with :focus-visible or :focus-within.

    Five checks for your own project

    • Unplug your mouseUse Tab, Shift+Tab, Enter and Space. Can you reach and use everything? Can you always see where you are?
    • Zoom to 200%Press Ctrl or Cmd and + a few times. Nothing should overlap or get cut off.
    • Check contrastBody text needs at least 4.5 : 1 against its background. Use the contrast checker above.
    • Read the headings aloneDo h1, h2 and h3 make a sensible outline of the page, in order?

    Key ideas

    • Accessibility helps people with visual, hearing, mobility and cognitive disabilities, and everyone else too.
    • WCAG's four principles: perceivable, operable, understandable, robust.
    • The browser builds an accessibility tree from your HTML: role, name and state. The right element gets them right.
    • Text needs 4.5 : 1 contrast; never use color alone to show meaning.
    • display: none hides from everyone; a visually-hidden class hides from the screen only.

    Common mistakes

    • Clickable divs and spans. They can't be reached with Tab.
    • outline: none with no replacement focus style.
    • Placeholder text used as the only label.
    • Things that only appear on :hover or mouseover, so keyboard users never see them.
