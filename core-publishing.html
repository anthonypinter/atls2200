What are the options?

Publishing means copying your site's folder onto a web server, so anyone can request its files. There are three main ways to do it, from most control to least effort.

Getting hosting and a domain name

For full control, you rent two things. Hosting is space on a web server, paid monthly or yearly. A domain name, like bouldertrailclub.org, is rented yearly from a company called a registrar. You point the domain at the server, and visitors can find you.

Publishing to your server

To get files onto rented hosting, you usually use an SFTP program, which shows your computer's folder on one side and the server's on the other. You drag files across. It works, but it's easy to forget a file or overwrite the wrong one.

Using a web-based IDE such as CodePen

Sites like CodePen and Glitch let you write HTML, CSS and JavaScript in the browser and see the result straight away, with a link to share. They're great for experiments, but they're not built for a full multi-page site that you own.

Using an online publishing tool

Services like GitHub Pages, Netlify and Cloudflare Pages host plain HTML, CSS and JavaScript sites for free, at an address like you.github.io. You can add your own domain later.

Git and GitHub, in brief

GitHub Pages publishes straight from a GitHub repository, so it helps to know four words:

  • Git is version control: it records snapshots of a project, so you can see what changed and go back if something breaks.
  • A repository ("repo") is a project folder that Git tracks. On GitHub, it lives online.
  • A commit is one saved snapshot, with a short message saying what changed: "Add trail map page".
  • A push sends your commits from your computer up to GitHub. GitHub Pages republishes the site after each one.

You don't need to learn Git's commands yet. GitHub's website and the GitHub Desktop app can do all of this with buttons.

Get the files ready

Most first-publish problems come from paths that only ever worked on your own computer. Before you publish, check that:

  • The home page is called exactly index.html, at the top of the folder.
  • Every file and folder name is lowercase with hyphens, and every path matches it letter for letter.
  • No path starts with file:/// or C:\: those point into your hard drive.
  • Paths use forward slashes, and don't start with / (that breaks on GitHub Pages project sites).

    What approach would we recommend? GitHub Pages

    For this course, publish with GitHub Pages: it's free, it handles HTTPS for you, and it republishes every time you push.

    1. Make a GitHub accountPick your username carefully: it becomes part of your site's address.
    2. Create a new repositoryClick New, give it a short lowercase name like trail-site, set it to Public, and create it.
    3. Add your filesClick “Add file”, then “Upload files”. Drag in the contents of your project folder, so index.html sits at the top level. Write a commit message and click Commit changes.
    4. Turn on PagesOpen Settings, then Pages. Under “Build and deployment”, choose “Deploy from a branch”, pick main and / (root), and click Save.
    5. Wait, then visitIt takes a minute or two. Refresh the Pages settings to see your link. Each time you commit a change, give it another minute.
    Where will my site be?

    If it doesn't work
    I get a 404 page

    Check there's a file named exactly index.html, all lowercase, at the top of the repository, not inside another folder. Then wait a couple of minutes and refresh.

    The page shows, but with no styles or images

    A path is wrong. Open DevTools, look at the Console and Network tabs for 404s, and compare each path with the file names in the repository, capital letters included.

    My changes don't show up

    Wait a minute after committing, then do a hard refresh (Ctrl/Cmd + Shift + R) to skip the browser's cache.

    Key ideas

    • Publishing copies your folder onto a web server that anyone can reach.
    • Options: rented hosting plus a domain, an online code editor, or a free publishing service.
    • GitHub Pages publishes a repository at username.github.io/repository/.
    • A commit is a saved snapshot; pushing sends commits to GitHub, which republishes the site.
    • Check paths before publishing: lowercase, relative, forward slashes, nothing from your own disk.

    Common mistakes

    • Uploading the project folder instead of its contents, so index.html ends up a level too deep.
    • Paths starting with file:///, C:\ or /.
    • Capital letters that worked on a Mac or Windows laptop but not on the server.
    • Expecting changes to appear instantly. Give it a minute, then hard-refresh.
