Debugging CSS

When CSS doesn't do what you expect, don't guess and reload. Your browser's developer tools show exactly which rules apply to each element, which lost, and why, and let you try fixes live.

You'll be able to

  • Open DevTools and inspect any element.
  • Explain why the DOM in DevTools can differ from your source code.
  • Read the Styles pane: find crossed-out declarations, edit values and add properties.
  • Work through a checklist when CSS doesn't apply: validity, support, overrides and a reduced test case.

How to access browser DevTools

Every desktop browser has DevTools built in. You'll use them every day from now on.

Inspect one elementRight-click it on the page and choose Inspect. DevTools opens with that element selected.
Open DevToolsF12 or Ctrl+Shift+I on Windows. Cmd+Option+I on a Mac. In Safari, turn on "Show features for web developers" in Settings first.
Test on a phone sizeClick the device toolbar icon (a phone and tablet) at the top of DevTools to preview any screen width.
Changes aren't savedEdits in DevTools disappear when you reload. Once you've found the fix, copy it into your CSS file.

The DOM versus view source

View source (Ctrl/Cmd+U) shows the HTML file exactly as the server sent it. DevTools' Elements panel shows something different: the DOM, the tree the browser actually built. They can differ, because the browser repairs mistakes, adds elements the rules require (like <tbody> in a table), and JavaScript can change the page after it loads. When debugging, the DOM is the truth: it's what your CSS is matched against.

Inspecting the applied CSS

  


Right-click an element and choose Inspect. On the right of the Elements panel, the Styles pane (called Rules in Firefox) lists every rule that matches the selected element, most specific at the top, with the file name and line number of each. Declarations that lost are crossed out; look higher up to find what beat them. Rules marked user agent stylesheet are the browser's defaults: you can't edit them, but your CSS can override them. Shorthands like margin can be expanded to see their longhands.

    
Each declaration has a checkbox: untick it to switch it off and see what changes.

    
Editing values

    
Click any value to edit it. Colours open a colour picker. Changes apply instantly, but only in your browser, until you reload.

    
Adding a new property

    
Click just inside the closing brace of a rule (or in the element.style box at the top) to add a declaration. DevTools autocompletes property names and values as you type.

    
Understanding the box model

    
The Computed or Layout tab shows a diagram of the selected element's content, padding, border and margin, with real pixel sizes. It's the fastest way to find out where unexpected space comes from (more on that in the next lesson).

    
Solving specificity issues

    
If a declaration is crossed out, the rule above it won. Compare the two selectors' specificity, then fix your CSS: a more specific selector, a later rule, or less specific competition. Don't reach for !important.

    
Watch out
Changes made in DevTools disappear when you reload. Once a fix works, copy it into your real CSS file.

Debugging problems in CSS

  


When something won't work, work through these in order:

    
Take a step back from the problem

    
Stuck for a while? Take a break, or explain the problem out loud to someone (or something). The fix is often obvious with fresh eyes.

    
Do you have valid HTML and CSS?

    
Browsers silently ignore CSS they don't understand: a misspelled property, a missing unit, a missing semicolon. Nothing turns red on the page. Run your files through the W3C HTML validator and CSS validator, and look for declarations DevTools shows with a warning icon.

    
Are the property and value supported?

    
Newer features may not work in every browser. Check the browser compatibility table at the bottom of any MDN property page. DevTools also flags unsupported declarations.

    
Is something else overriding your CSS?

    
Look for your declaration crossed out in the Styles pane, and see which rule beat it.

    
Make a reduced test case

    
If you still can't find it, rebuild the problem from scratch in as little code as possible:

    
    
      
  1. Copy just the HTML that shows the problem into a new file, or a playground like CodePen.

  2. Add only the CSS that affects it.
    3. 
      
  3. Remove things one at a time until the problem disappears. The last thing you removed is involved.
    4. 
      
  4. If it's still a mystery, you now have a tiny example to ask someone about.

    Key ideas
    
      
      
        
    • The DOM in DevTools is what your CSS matches against, not your source file.
      • 
        
    • The Styles pane lists every matching rule; crossed-out declarations lost.
      • 
        
    • The file name and line number next to each rule tell you where to make the fix.
      • 
        
    • Browsers silently ignore invalid or unsupported CSS. Validate, and check MDN's compatibility tables.
      • 
        
    • A reduced test case isolates a bug, and makes it easy to ask for help.
      • 
      
    
    
    
    
    
      
    Common mistakes
    
      
      
        
    • Fixing the problem in DevTools and forgetting to copy the fix into the real file.
      • 
        
    • Searching your CSS for a rule that's actually the browser's default.
      • 
        
    • A rule that's missing completely, from a selector typo or a stylesheet that didn't load.
      • 
        
    • Typos the browser ignores without complaint: colour, 16 px, a missing semicolon.
      • 
        
    • Debugging the wrong element. Check which element is selected in the tree.
