Organizing CSS

CSS doesn't care how your stylesheet is arranged. You do, the next time you need to change something and can't find it. A few habits, and a naming system or two, keep a stylesheet easy to work with as it grows.

You'll be able to

  • Format and comment a stylesheet so it's easy to read and search.
  • Group rules into sections in a consistent order, and keep specificity low.
  • Name classes with a methodology like BEM.
  • Describe what preprocessors like Sass and build tools do.

Tips to keep your CSS tidy

Does your project have a coding style guide?

If you're working with a team, or on an existing project, check whether there's a style guide first. Following the team's conventions matters more than your own preferences: a stylesheet written five different ways is harder to work with than one written any single way.

Keep it consistent

Whatever rules you choose, use them everywhere: the same way of naming classes, the same color format (all hex, or all rgb()), the same indentation. Consistency means you can predict where things are and how they're written.

Formatting readable CSS

Some people write each rule on one line; most put each declaration on its own line, which is easier to scan and gives cleaner diffs in version control. Either is fine as long as you're consistent.

Comment your CSS

    
Comments help the next person, including you in six months. Use them for two things. First, section headings, written in a way that's easy to search for. MDN suggests ||, which rarely appears anywhere else, so searching for || jumps from section to section:

    
/* || General styles */
/* || Utilities */
/* || Site-wide */

    
Second, explain anything surprising, like why a rule exists:

    
.box {
  background-color: red; /* fallback for browsers without gradients */
  background-image: linear-gradient(to right, #ff0000, #aa0000);
}

    
Create logical sections in your stylesheet

    
A good order runs from general to specific:

    
    
      
  1. General styles for plain elements: body, p, headings, lists, links, tables.
    2. 
      
  2. Utility classes: tiny one-job classes like .no-bullets or .text-center.
    3. 
      
  3. Site-wide components: things on every page, like .main-nav and .logo.
    4. 
      
  4. Specific components and pages: cards, the trail page, the sign-up form.
    5. 
    

    
Because later rules win ties, this order also means the specific stuff naturally overrides the general.

Avoid overly-specific selectors

  


A selector like article.main p.box only works in one exact place, and its high specificity makes it hard to override. Then the override needs an even longer selector, and eventually !important. Style with single classes instead: .box works wherever you put it.

Break large stylesheets into multiple smaller ones

  


On a big site, one huge file gets hard to navigate. You can split it, for example into a global stylesheet and one per section, and link them in order. Rules in later files win ties, just as later rules in one file do:

    
<link rel="stylesheet" href="global.css">
<link rel="stylesheet" href="trails.css">

CSS methodologies

    
Some teams follow a published set of rules for writing CSS, called a methodology. Two well-known ones:

    
    
      
  • OOCSS (Object-Oriented CSS) separates reusable patterns into classes. A common "media object", an image beside some text, gets one .media class reused everywhere, instead of being styled again in each place.
    • 
      
  • BEM (Block, Element, Modifier) is a naming system. A block is a standalone component (.card). An element is a part of it, joined with two underscores (.card__title). A modifier is a variation, joined with two hyphens (.card--featured). The names are long, but you can tell from a class alone what it belongs to.
    • 
    

    
Others include SMACSS, ITCSS and Atomic CSS. You don't need one for a small project, but you'll meet them on bigger ones.

Build systems for CSS

    
Larger projects often run CSS through tools before it reaches the browser.

    
A preprocessor like Sass adds features to CSS and compiles your files into plain CSS. Sass variables ($brand: #2340d9;) came before CSS had its own; today native CSS variables do the same job in the browser. Sass is still popular for splitting styles into small partial files and combining them with @use:

    
// main.scss
@use "base";
@use "layout";
@use "components/card";

    
A post-processor works on the finished CSS: for example, cssnano strips comments and spaces to make the file smaller. Your readable, commented source stays readable; the browser gets the small version.

Key ideas

      
    
        
  • Follow the team's style guide; whatever you choose, be consistent.
    • 
        
  • Use searchable section comments like /* || Base */, and comment anything surprising.
    • 
        
  • Order sections from general to specific: base, utilities, site-wide, components.
    • 
        
  • Keep specificity low: single classes, not long chains or IDs.
    • 
        
  • BEM: .block, .block__element, .block--modifier.
    • 
      

    

    

      
Common mistakes

      
    
        
  • Adding every new rule to the bottom of the file.
    • 
        
  • Names like .box2, .new or .left that stop making sense later.
    • 
        
  • Overriding a long selector with an even longer one, then !important.
    • 
        
  • Leaving old, unused rules in "just in case". That's what version control is for.
